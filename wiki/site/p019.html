Лабораторная работа №1 — пороги AGT budgets без LLM

Статус: проект по исходникам; пользователем в VM не выполнена. Сначала пользователь проходит ЛР №0 — подготовка отдельной Ubuntu Server VM; методичка №0 существует, но пока не исполнена и не принята. До подтверждения её протокола команды ниже не запускать. Агент не управляет VirtualBox и не исполняет код из ZIP на хосте.

Цель и задачи

Изучить оригинальную декларативную политику ограничения budget counters в блоке L3 схемы; проверить различие между числовым порогом, некорректным счётчиком и отсутствующим snapshot. Это соответствует части ЧТЗ о политиках рабочих процессов и доступности, но не проверяет работу всего агента, сетевой rate limiting или фактическое прекращение уже выполняемого инструмента.

Задачи: (1) подтвердить идентичность оригинальных файлов по хешам; (2) выполнить штатные тесты автора; (3) сравнить четыре искусственных входа с ожидаемым policy verdict; (4) зафиксировать случай, в котором verdict не выдаётся; (5) сохранить реальные результаты и объяснить границу проверки.

Источник и теория

Оригиналы: budgets.rego и budgets_test.rego, копии из ACS ZIP, SHA-256 и лицензии — в карточке переноса. package agt.budgets, import rego.v1. Вход политики — input.snapshot.envelope.budgets, пороги — аргумент deny_if_budget_exceeded(thresholds). При числовом счётчике >= лимита возвращается объект с decision: deny; при присутствующем нечисловом счётчике причина budget_counter_invalid. Если snapshot отсутствует полностью, исходный тест ожидает отсутствие verdict, а не deny. Отсутствующий verdict должен отдельно обрабатываться доверенным вызывающим кодом; в этой ЛР такого host enforcement нет.

Источники команд: официальные OPA Policy Testing и OPA CLI Reference. Они подтверждают формы opa test, --fail-on-empty, opa eval --data --input. Для ЛР №0 предложена версия OPA 1.21.0, но её фактический хеш и доступность в госте ещё должны быть подтверждены пользователем; команды ниже — проект для гостя, не свидетельство запуска.

Подготовка и условия остановки

  • ХОСТ — пользователь: после готовности отдельной VM и её чистого снимка передать только этот пилотный комплект способом, выбранным в ЛР №0. В режиме испытаний выключить сеть и общие каналы согласно плану 0.2. На хосте не запускать OPA/архивный код для этой ЛР.
  • ГОСТЬ — пользователь: убедиться, что установлен проверенный OPA с поддержкой rego.v1; записать вывод opa version и хеш бинарника в отчёт. Точный способ снабжения/версию фиксирует ЛР №0; если OPA нет — остановить опыт, не скачивать произвольный бинарник в режиме испытаний.
  • ГОСТЬ — пользователь: располагать копией каталога проекта так, чтобы относительные пути ниже разрешались из labs/01-agt-budgets/. Если дерево перенесено иначе, скорректировать только аргументы путей команды, не менять оригинальные .rego.
  • Если исходный тест не проходит, JSON не читается или вывод отличается от ожидаемого, сохранить stderr/stdout и версию OPA; не исправлять оригинальную политику и не записывать опыт как успех.

Ход работы (только в госте после ЛР №0)

  1. ГОСТЬ: открыть терминал в labs/01-agt-budgets/; зафиксировать opa version, хеш бинарника, состояние сети, имя чистого снимка VM и SHA-256 двух .rego и LICENSE-AGT. Ожидается совпадение хешей с карточкой оригинала. Сохранить команды и вывод в журнал опыта.

  2. ГОСТЬ: выполнить штатные тесты автора, не передавая каталог upstream/ целиком (это загрузило бы другие Rego/data-файлы):

    opa test --fail-on-empty -v ../../originals/agt-budgets/upstream/reference-implementations/agt/policy/lib/budgets.rego ../../originals/agt-budgets/upstream/reference-implementations/agt/policy/lib/budgets_test.rego

    Ожидание по статическому чтению: тесты на счётчики, пороги, malformed и missing snapshot обнаружены и должны пройти; фактическое число PASS/FAIL занести только после опыта. Вывод и exit code сохранить.

  3. ГОСТЬ: для каждого из четырёх файлов inputs/*.json выполнить одинаковый policy query, меняя только --input:

    opa eval --format pretty --data ../../originals/agt-budgets/upstream/reference-implementations/agt/policy/lib/budgets.rego --input inputs/01-below-limit.json 'data.agt.budgets.deny_if_budget_exceeded(input.thresholds)'

    Повторить для 02-at-limit.json, 03-malformed-present.json, 04-missing-snapshot.json. Сохранить полный вывод и exit code каждого вызова, не интерпретировать один только exit code как allow или deny.

  4. ГОСТЬ: заполнить таблицу ниже фактическими verdict/ошибками, сравнить со штатными тестами и объяснить, почему undefined/пустой результат — не разрешение само по себе и не доказанный блок. Не вызывать настоящий инструмент; эффекта ОС в этой ЛР нет.

  5. ГОСТЬ: сохранить протокол и скриншоты реального экрана, выключить гостя; откат к чистому снимку выполнить по необходимости. Чистый снимок не считать отменой внешних эффектов (в этом опыте внешних действий не планируется).

Требования к отчёту и контрольные вопросы

Отчёт: исполнитель и дата; цель; среда (гостевая ОС, версия/хеш OPA, снимок, сеть); хеши оригиналов; фактические команды, выводы, exit codes; таблица выше; реальные подписанные скриншоты при наличии; неожиданные ошибки и честный вывод. Не включать настоящие секреты и личные данные. Критерий успешного policy-level опыта — штатные тесты обнаружены и пройдены, четыре запроса дали ожидаемые решения или документированное расхождение. Это не критерий безопасности всего агента.

Вопросы: (1) кто обязан формировать доверенный budget counter? (2) чем >= отличается от > на границе лимита? (3) почему present malformed и missing snapshot ведут себя по-разному? (4) что произойдёт, если вызывающий host трактует отсутствие verdict как allow? (5) что требуется, чтобы доказать блокировку настоящего инструмента? (6) почему этот опыт не доказывает сетевой rate limiting и ОС-песочницу?
