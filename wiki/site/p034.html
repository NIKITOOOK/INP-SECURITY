M-AGT-APPROVAL — оригинальные правила согласования AGT

Статус: пример карточки; исходник сравнен, родной runtime не запускался. Карта · Ручные опыты.

Где расположен и для чего нужен

Архитектура: L3 → Human-in-the-Loop; связи с пользовательским подтверждением и администрированием. Вклад в целостность: механизм сообщает исполнителю, что действие должно пройти согласование. Сам helper не показывает диалог и не останавливает инструмент: это обязанность вызывающего runtime, которую нужно испытать отдельно.

Происхождение

  • Репозиторий из реестра: https://github.com/GenAI-Security-Project/agent-control-standard .
  • Архив: agent-control-standard-integration.zip.
  • Файл внутри ZIP: agent-control-standard-integration/reference-implementations/agt/policy/lib/approval.rego.
  • SHA-256 исходного файла, полученный прямым чтением ZIP: 117207eb032e486b20ecfae0591b37d8482faa0515ff130ff82a3f9b3cf30805.
  • Commit-кандидат из комментария ZIP: dc265475139a922824f0c817e2ecc2a2ce31c06c. Принадлежность репозиторию и соответствие файла ещё не проверены; это не подтверждённая постоянная ссылка.
  • Лицензия по текущему реестру и заголовку файла: MIT, Microsoft Corporation. Лицензионный файл должен сопровождать оригинал при подготовке A2.
  • Исходные тесты по реестру: reference-implementations/agt/policy/lib/approval_test.rego; их полный разбор и запуск относятся к A1/A4.

Принцип

В файле есть helpers escalate_if, escalate_if_approver_required, escalate_with_message. Они формируют verdict escalate при выполнении соответствующих условий. Исполнитель должен обработать verdict, запросить согласование и не продолжить действие раньше разрешения. В исследовании нужно отдельно подтвердить путь «helper → host approval resolver → выполнение».

Текущий Python-шлюз преобразует это в собственный require_review; такое преобразование не является неизменённым методом AGT. Отсутствие результата Rego тоже нельзя автоматически переводить в разрешение: точное правило определяется оригинальным вызывающим кодом и тестами.

Точность существующей копии

Локальный файл: approval.rego.

SHA-256 локального файла: 6bf9faa9bfc07d8d018095e415742bcd8f13b9bf721acf4e2b270691407d5cb7.

Прямой diff показал удалённые поясняющие комментарии и свёрнутое форматирование объектов. Побайтное равенство: НЕТ. Это не свидетельство изменения логики, но нарушает выбранный пользователем критерий неизменённого оригинала. Существующая копия сохраняется для сравнения; точная копия должна храниться отдельно.

Предстоящий ручной опыт

После определения версии OPA/Rego и входного контракта пользователь в VM запускает исходные тесты, затем по одному вызывает helper с входами из этих тестов. Он сравнивает verdict и отсутствие verdict, открывает лог и отмечает фактическое значение. Следующий отдельный опыт проверяет остановку тела инструмента до согласования в родном host-пути, если этот путь доступен локально.

Точные команды и ожидаемые JSON добавляются только после чтения исходных тестов. Сейчас результата запуска нет; подтверждена только статическая сверка файла.
