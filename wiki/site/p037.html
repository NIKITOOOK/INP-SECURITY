A1.3/13 — GenAI Data Security Initiative: статический сканер и проверка трасс

Дата: 27.09.2026. Источник: GenAI-Data-Security-Initiative-main.zip, 1 712 370 байт, SHA-256 1C2FB9907F2B25330655CA52A3B28F3D72DE51FF788F2C4735EE52F5ED06EF85, 832 элемента. ZIP открылся штатно; выборочные файлы прочитаны и хешированы без распаковки/исполнения. Полная CRC-проверка всех элементов не проводилась. Корневой LICENSE обозначает CC BY-SA 4.0; условия повторного использования содержимого и кода нужно учитывать отдельно до переноса в общий Git. Точный commit ZIP не установлен.

Вывод по назначению

Архив сочетает таксономию рисков, датасеты и DSGAI Scanner v0.3.0. Сканер действительно содержит исполняемый статический анализ исходников: скомпилированный JSON-набор имеет 107 PCRE-правил (85 structural, 22 value_bearing) для 21 DSGAI-контроля. Это инструмент аудита кода, а не middleware на маршруте вызова инструмента агента. Он может подсказать, что проверить вручную, но не способен сам остановить опасное действие агента во время выполнения.

Соответствие нашей схеме

Блок Найденный механизм Граница доказательства
L1 / вход и контекст Правила сканера ищут в исходниках признаки работы с документами, RAG, промптами и избыточным контекстом. Трассы описывают источник данных и движение между агентом и инструментом. Это статические признаки, не детекция prompt injection в текущем пользовательском вводе, не Spotlighting и не sandwiching.
L2 Таксономия помогает описать повышение недоверенного содержимого и утечки контекста. В исследованных частях нет реализации ролевых эмбеддингов, fine-tuning или модельной иерархии; таксономия не заменяет механизм.
L3 / конфигурации, секреты, лимиты Набор правил включает шаблоны hardcoded API keys, wildcard tool permissions, MCP auth/schema, timeout/rate-limit и т. п. CLI классифицирует контроль как FAIL, WARN, PASS, NOT VALIDATED или NOT APPLICABLE; результат может уйти в JSON/SARIF. PASS возникает от найденного pass_signal в коде — это не проверка фактического запрета или корректности настройки. Если шаблон не найден, обычный итог NOT VALIDATED, а не доказанная безопасность. Inline suppressions и baseline меняют CI-gate, не поведение агента.
Секреты / публикация результатов Для value_bearing-правил CLI вызывает rg --only-matching --replace '', сохраняет путь/строку без совпавшего значения; checkpoint запрещает поля match_text, content, value, raw_grep_output. Тесты проверяют отсутствие тестового секретного фрагмента в выходах. Гарантия узкая: касается значения, распознанного соответствующим правилом. Структурные правила читают строку в процесс сканера; пути/номера строк могут быть чувствительными. Перед публикацией нужен ручной просмотр JSON/SARIF/HTML. Документ о benchmark прямо говорит, что precision ещё не размечена и чисел нет.
Сеть и воспроизводимость CLI требует локальный rg с PCRE2. По умолчанию CVE-enrichment может запросить OSV/NVD; --no-cve или --offline меняют этот контур. При ошибке enrichment скан продолжается с заметкой. «Детерминированный» относится прежде всего к pattern matching на фиксированных файлах/правилах. Время, Git-состояние и внешнее CVE-обогащение не тождественны при каждом запуске. В рамках A1 код/сеть не запускались.
Шина событий, коннекторы, память agentdataflow_toolexchange_traces задаёт JSON Schema для событий/спанов: actor, операция, чувствительность, происхождение, finding и связь с DSGAI. Валидатор проверяет схему, порядок parent/child, сопоставление finding, provenance и типовые секреты/адреса во всех строковых полях. В ZIP уже есть три entry, хотя README этого поднабора ещё говорит, что каталог пуст. Это формат и проверка сохраняемых исследовательских трасс, не реальная внутренняя шина Core-Agent и не DLP в рантайме. Валидатор сам признаёт: он не проверяет правдивость цитаты и может пропустить секрет, не похожий на его шаблоны. sanitization.attestation остаётся заявлением автора.
Заглушки data_validation/validators/anonymization_scanner.py перечисляет regex, но scan_file() — pass, а CLI печатает, что это stub. Нельзя учитывать этот файл как работающий DLP/анонимизатор. Реальные проверки трасс находятся в другом модуле — datasets/.../validate.py.

Что применять на следующих этапах

  1. Из этого ZIP разумно брать методику статического аудита и схему доказательств, не вставлять 107 regex в L1/L3 runtime как «политику». Если выбирать оригинал для A2/A4, сначала подтвердить лицензионный режим, зависимости rg/PCRE2, разрешённый offline-профиль и заранее определить контрольный тест на ложные результаты.
  2. Схема трасс пригодна как пример для будущих лабораторных: tool_call → решение политики → факт исполнения → наблюдаемый эффект, с отдельными provenance и synthetic payload. Но нельзя подменить ею уже существующую шину агента или записать гипотетическую трассу как фактическое наблюдение.
  3. При оценке собственного проекта PASS сканера записывать лишь как «признак механизма найден в коде». Прямой запрещённый вызов и отсутствие эффекта проверяются на A4 отдельно. Метрики precision без ручной разметки не заявлять.
  4. Пользовательские документы и правила сканера являются исследуемыми данными, не командами к установке. В этом пакете не запускались Python, ripgrep, CVE API или внешняя модель.
