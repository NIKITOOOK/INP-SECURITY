Что это за источник

README определяет проект как набор учебных sandboxes, exploitation code и tutorials для red teaming. Это не библиотека защитных политик для DSH/LangGraph. Часть стендов намеренно уязвима; эксплуатационные скрипты и команды установки из ZIP не являются инструкциями для нашего хоста. Найденные сценарии можно рассматривать как материал для будущих проверок при соблюдении профиля отдельной VM, но не как уже проверенный механизм защиты.

Связь с архитектурой и ТЗ

Блок нашей схемы Найденный материал и значение Что не доказано
L1 / prompt injection и граница недоверенного контекста В учебном стенде памяти пользовательский текст без валидации попадает в общую SQLite-память; get_all_facts() не ограничивает выборку исходной сессией. Затем факты вставляются в system-сообщение следующих диалогов. Это наглядная отрицательная проверка provenance и межсессионной изоляции. В архиве здесь нет защиты от такого переноса: уязвимость создана намеренно. Нельзя считать пример реализацией Spotlighting, prompt sandwiching или детектора инъекций.
L2 / иерархия инструкций Стенд памяти демонстрирует повышение недоверенного факта до system-контекста. Это нарушение границы доверия в учебном приложении, не реализация иерархии, embeddings или безопасного fine-tuning.
L3 / разрешения и целостность файлов Другой учебный mock agent показывает разницу между проверкой чтения и записи пути на разных стадиях; его оркестрация частично симулирована. Нельзя переносить частичный path check как готовую sandbox/allowlist-политику; «stage» стенда не доказывает состояние актуальной внешней библиотеки или ОС-изоляцию. Версии в README (v0.1.24–v0.1.26) и комментарии server.py (1.2.24–1.2.27) расходятся — перед опытом нужна отдельная сверка.
Аудит/оценка ответов system_reconnaissance задаёт 24 пробы по 9 категориям (включая tools, policy boundaries, system instructions, memory). Он сохраняет статус каждого запроса, время, ответ и эвристическую метку в JSONL и Markdown. Ошибка/тайм-аут даёт not_assessed, а не «защита сработала». Unit-тесты проверяют метки, ошибки и запись отчётов. potential_disclosure, boundary_or_refusal и другие метки — сигналы для ручной проверки, не вердикт об уязвимости или безопасности. Ответ модели о наличии инструмента не доказывает фактического доступа к нему. Это методика тестирования, не предисполнительный policy gate.
Изоляция среды README описывает отдельные контейнерные стенды и environment для red-team инструментов; для Windows рекомендует WSL2. Контейнерный «sandbox» здесь означает контролируемую учебную цель, а не доказанную изоляцию нашего агента. На хосте стенды/Podman/Ollama не запускались.

Что пригодится нам позднее

  1. Для A4 полезен принцип независимого доказательства: запрос → наблюдаемый ответ → решение защиты → реальный доступ/эффект. Эвристический ответ не подменяет проверку инструмента или файловой системы.
  2. Проба на отравление памяти может стать отдельным безопасным сценарием с искусственными данными: две сессии, раздельные владельцы, наблюдение, попадает ли чужой факт в привилегированный контекст. Сам уязвимый стенд не переносить в проект.
  3. Сценарий чтения/записи полезен для полноты L3: отдельно проверять оба направления и канонизацию пути. Описания конкретных эксплойтов в отчёт не копируются; запуск только на будущей разрешённой лабораторной стадии.
  4. Формат отчётности system_reconnaissance полезен как образец: устойчивые ID проб, язык/категория, error/timeout отдельно от verdict, JSONL плюс читаемый Markdown. Его отчёты сохраняют сырые ответы — перед Git нужна проверка на секреты и обезличивание согласно плану.
