# Поиск источников при отладке

[Главная Wiki](README.md) · [Неудавшиеся проверки](Неудавшиеся_проверки.md) · [Статусы источников](Источники_и_статусы.md)

Рабочая заметка пользователя, оформлена 01.10.2026: при проблеме рано подключать поиск, а не тратить много попыток на догадки. Это порядок исследования, не разрешение автоматически применять найденные команды.

1. Зафиксировать точную ошибку, команду, версию и границу среды: хост / VM / сервис. Отделить ожидаемое от фактического.
2. Сделать 2–3 запроса: точный текст ошибки; продукт + версия + симптом; запрос по официальной документации или issue-трекеру. Не отправлять в поиск токены, пароли, личные пути и закрытые журналы.
3. Использовать Google AI/другую поисковую LLM для гипотез и обнаружения ссылок. Если ответ недоступен, продолжать обычный поиск; не приписывать ему неувиденное содержание.
4. Открыть первоисточники ответа и проверить, что они действительно подтверждают совет, относятся к нужной версии и среде. Ответ LLM и поисковый сниппет сами по себе не доказательства.
5. Выбрать минимальную проверку с наблюдаемым результатом. Политики и исследуемый код проверять только в разрешённой VM. Изменение доверия сертификатам, отключение TLS, расширение прав, сети или установка ПО не следуют автоматически из совета.
6. Записать запросы, прочитанные адреса, гипотезу, выбранную проверку, фактический результат и нерешённые вопросы. HTTP 200 с усечённым текстом отмечать как частичный доступ.
7. Если проверка невозможна — сохранить конкретный блокер. Не объявлять найденное исправление применённым и не скрывать неудачный опыт.

Пример из предоставленного отчёта: SELF_SIGNED_CERT_IN_CHAIN — сообщённая ошибка. Причина, связанная автором с антивирусным сертификатом, остаётся гипотезой до нашей проверки. Совет «отключить проверку сертификатов» не является допустимым автоматическим исправлением.
