# Программа проверки политик в Azure VM — A3–A4

Редакция: 0.2, 28.09.2026. Статус: уточнённый проект к согласованию вместе с планом 0.3. Основание смены стенда — [D-009](logs/Решения.md); исходные требования и пробелы — [матрица ЧТЗ](wiki/аудит/Матрица_требований_ЧТЗ_A1.1.md) и [матрица A1.4](wiki/аудит/Матрица_покрытия_A1.4.md). Этот документ задаёт **будущую проверку**, а не сообщает о проведённых испытаниях. Сведения о существующей VM взяты из протокола другого сеанса; в этом уточнении Azure не запускалась и её конфигурация не проверялась заново.

## Цель и граница утверждений

Azure VM нужна не для одной демонстрации, а для последовательной проверки всех **применимых найденных исполняемых методов безопасности** из корпуса 14 ZIP. У каждого метода должен появиться воспроизводимый опыт либо конкретный, подтверждённый блокер. Все строки нашей части ЧТЗ и L1/L2/L3 должны иметь статус; для метода, которого в исходниках нет, VM не может создать доказательство его работоспособности. «Корпус учтён полностью» не равно «все политики работают».

Уточнение пользователя 28.09.2026: Azure найден через студенческие возможности GitHub; VM уже создана, нужно понять, сможет ли агент удалённо испытывать в ней наши наработки. **Это предлагаемый маршрут, техническая доступность которого из текущего чата пока не доказана:** файлы проекта на D: → проверенный перенос в Azure Ubuntu → выполнение тестов внутри гостя → проверенные результаты обратно на D:. Документация Azure подтверждает механизмы SSH/Run Command, но не доступ, авторизацию и возможность автоматизации данного агента. Пользователь сообщил о неуспешной попытке подключения; её точная команда и ошибка пока неизвестны. До успешной контрольной проверки не писать «агент сможет подключиться». Наличие локального SSH-клиента не означает ни установленного соединения, ни локального исполнения тестов. Подключение само по себе также не предоставляет гостю локальные файлы — их надо передать отдельно.

Испытывать два различимых комплекта: (1) оригиналы из ZIP по A2/A4; (2) существующие собственные/адаптированные `policy-gateway` и адаптеры — как отдельное сравнительное испытание после проверки зависимостей. У них разные хеши, протоколы и выводы; успех одного комплекта не засчитывается другому. Это предложение проверки уже созданного кода, без возобновления разработки ядра или gateway.

Испытание оригинала в отдельной VM доказывает только заявленную границу этого оригинала. Проверка собственного тестового вызова не равна интеграции в агент команды; решение policy engine не равно запрету реального действия. Эти уровни записываются независимо. Не обещать успешного исполнения каждого из 14 проектов: часть ZIP содержит рекомендации, уязвимые примеры или внешние сервисы, а не готовую политику для нашего агента. Непригодность фиксируется с точным основанием, без тихого исключения.

## A2.2 — реестр, который управляет всей серией лабораторных

Предварительная оценка применимости — инженерный вывод из аудита исходников, **не результат запуска**:

| Предмет проверки | Что можно проверять на Ubuntu VM в Azure | Что остаётся открытым |
|---|---|---|
| L1: валидация, обработка недоверенного текста, найденные prompt-приёмы | Переносимые функции/конфигурации и маршруты передачи данных | Наличие конкретного оригинала и зависимостей; эффект на настоящей модели проверяется отдельно |
| L1: детекторы NeMo/другие | Реальный детектор при доступных весах, памяти и лицензии | Достаточность 4 ГиБ не установлена; эмуляция ответа сервиса не является испытанием детектора |
| L2 | Доступные конфигурации/поведение выбранной модели в пределах нашей роли | Ролевые эмбеддинги и fine-tuning требуют реализации, ресурсов и ответственности команды; Azure их автоматически не добавляет |
| L3: Rego, права инструментов, HITL, бюджеты, stop | Штатные тесты и маршруты до безопасного тестового эффекта | Требуются реальные counters, точка применения запрета, корректный учёт отмены; одно deny не доказывает эффект |
| L3: Linux sandbox/AppArmor/контейнеры | Проверку прав и изоляции внутри Linux-гостя при поддержке ядром/runtime | Состояние AppArmor, capabilities и контейнерного runtime проверяется; Windows AppLocker на Ubuntu не испытывается |
| Windows-, GPU-, nested-virtualization-зависимые методы | Только после отдельного выбора совместимой среды/размера | Текущий профиль не считать пригодным без проверки; оплачиваемые дополнительные ресурсы отдельно согласуются |
| Локальный агент по ЧТЗ | Облачную подготовку политик, тестовых входов и свидетельств | Подтверждение на целевом персональном компьютере и ядре команды — A4.4; облачная лаборатория не закрывает этот пункт |

Azure Policy/NSG относятся к управлению и сетевой границе стенда. YAML/Rego и middleware агента продолжают храниться в проекте как самостоятельные артефакты. Переписывать все решения под Azure SDK или заменять их managed-сервисами лишь ради переноса не требуется.

На основе [14 отчётов](wiki/аудит/Индекс_архивов_A1.3.md) и A1.4 создать одну строку **на каждый отдельный найденный механизм**, а не на архив: ID; требование/слой; ZIP и SHA-256; путь/символ/версия или непроверенный commit; лицензия; исходный тест; зависимости; проверяемое решение; точка реального enforcement; сценарии отказа и обхода; ресурсы; переносимые файлы; статус происхождения/исполнения/интеграции; ссылка на лабораторную и run-id. У каждого из 14 архивов должна быть ссылка на строки реестра либо мотивированное «нет применимой исполняемой политики». Пустых статусов не оставлять.

Оригиналы переносить отдельными наборами с хешами ZIP ↔ проект ↔ Azure VM, не редактируя дерево upstream. Входы, конфигурация, адаптеры наблюдения и логи — вне него. Если исходный механизм требует переписывания, это уже адаптация, для которой нужен отдельный метод и отдельный вывод; не выдавать её за проверку оригинала.

## A3 — приёмка Azure как экспериментального стенда

Порядок уточнён, чтобы решения принимались до изменения облака:

1. **A3.1 — паспорт пригодности:** зафиксировать доступные ресурсы и ответы Q1–Q7 ниже, определить класс первого опыта и конкретные границы. Можно выполнять по документам без запуска VM. A2.2-реестр дополняется параллельно; подготовка всей тяжёлой серии не нужна для приёмки среды первого пилота.
2. **A3.2 — схема доступа и снабжения:** подготовить конкретные настройки и способ входящего переноса/выгрузки логов с объёмом, контрольными суммами, стоимостью и возвратом в режим опыта. Применять в рамках разрешения D-009; новое платное решение — после согласования.
3. **A3.3 — проверяемый профиль опыта:** минимальные права процесса, разрешённые локальные адресаты, блокировка внешних/облачных полномочий, раздельный доступ администратора, сохранение логов и воспроизводимый откат. Проверка должна охватывать пользователя/процесс, которым позже запускается метод.
4. **A3.4 — приёмка:** заполнить протокол фактическими разрешёнными/запрещёнными проверками, доступом, хешами, восстановлением и расходами. Приёмка действует только для описанного профиля. Установка нового privileged runtime, GPU-среды или открытие API-доступа требует повторной проверки затронутых границ, а не автоматического переноса старой отметки.

Текущая VM [описана в протоколе](labs/00-environment/Протокол_Azure_A3.md): создана, но A3 не принята. Перед запуском политик проверить и сохранить факты:

1. Разделить **снабжение** и **опыт**. В снабжении допускаются только согласованные загрузки ОС/зависимостей из проверенных источников; исследуемый код не исполняется. В опыте — отсутствие публичного входа и проверяемая граница исходящих соединений. Уточнить влияние Azure management plane, Bastion и обновлений; отсутствие публичного IP не считать отсутствием egress. Отрицательную проверку провести из гостя и сохранить фактический вывод.
2. Выбрать перенос только нужных оригиналов и тестовых данных через контролируемый канал. Проверить SHA-256 до и после. Не переносить закрытый SSH-ключ, реальные секреты и личные документы. Если перенос требует временного сетевого режима, вернуть режим опыта и перепроверить его до запуска.
3. Зафиксировать чистую точку отката и проверить, что восстановление доступно. До создания снимка/дополнительного ресурса оценить стоимость хранения и получить решение пользователя. Снимок не отменяет внешние эффекты.
4. Записать версии ОС и подготовленных зависимостей, путь доступа, конфигурацию сети, отрицательную проверку egress, хеши, способ отката и процедуру остановки. Версию OPA до приёмки фиксировать по закреплённому релизу/хешу, а фактический `opa version` — после неё: не создавать круговое условие «для приёмки сначала исполнить запрещённый до приёмки OPA». По завершении сеанса подтвердить `Остановлено (освобождено)`; постоянные диски и другие ресурсы учитывать отдельно.
5. Если граница, доступ, перенос или откат не подтверждены — A3 остаётся заблокированной. `opa version`, штатные тесты и AGT запускать лишь после отдельной записи о принятии A3.

### Проверенные ограничения облака и решения для проектирования

- **Сеть и управление.** У NSG есть исходящие разрешения по умолчанию; private subnet и отсутствие публичного IP не заменяют проверку всего пути трафика. Для опыта требуется явное описание NSG/маршрутов и ограничений внутри гостя. Run Command требует исходящего 443 к Azure для возврата результата, запускает команды с повышенными правами по умолчанию и ограничивает возвращаемый вывод 4096 байтами. Поэтому его успешный вызов не доказывает отсутствие egress, а его вывод не считается полным журналом опыта. Для испытания отделить непривилегированный процесс от разрешённых административных каналов; широкое исключение `AzureCloud` всему процессу опыта не объявлять «полной изоляцией». [NSG](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-groups-overview), [Run Command Linux](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/run-command).
- **Платформенные адреса.** Учесть IMDS `169.254.169.254`, облачную identity и служебный адрес `168.63.129.16`: часть платформенного трафика не подчиняется обычным NSG-правилам. Проверить, назначена ли VM managed identity и какие у неё права; учебному процессу не передавать токены/CLI-сессию администратора. Ограничения для тестового процесса проектировать отдельно от системного агента Azure. Это отдельные проверки, а не утверждение о текущем состоянии VM. [IMDS](https://learn.microsoft.com/en-us/azure/virtual-machines/instance-metadata-service), [платформенный IP](https://learn.microsoft.com/en-us/azure/virtual-network/what-is-ip-address-168-63-129-16).
- **Передача файлов.** По протоколу создан Bastion Developer: штатная передача файлов native-клиентом для него не поддерживается, она доступна у Standard/Premium. Не закладывать SCP через Developer в методичку как готовый путь. Для малого комплекта возможно отдельно исследовать передачу точных байтов административным каналом с полной сверкой хешей; для большого комплекта — временный ограниченный канал снабжения. Выбор включает и выгрузку полных логов. Платный upgrade Bastion не выполнять по умолчанию. [Сравнение SKU](https://learn.microsoft.com/en-us/azure/bastion/bastion-sku-comparison).
- **Расходы.** Задать допустимую сумму за сеанс/месяц, длительность и ответственного за проверку deallocation. Диск, снимки и отдельные сервисы могут тарифицироваться после освобождения VM. Azure Budget уведомляет о превышении, но сам не останавливает расход. Студенческие кредиты/ограничение подписки сверить фактически; бесплатность всей лаборатории не предполагать. [Бюджеты](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets), [стоимость остановленных VM](https://learn.microsoft.com/en-us/cloud-computing/finops/best-practices/compute).
- **Граница тестов.** Сценарии из red-team корпусов ограничить собственными учебными объектами и синтетическими данными; внешние Azure-сервисы и чужие ресурсы не становятся целями опыта. Перед активными проверками уточнить применимые [правила Microsoft](https://www.microsoft.com/en-us/msrc/pentest-rules-of-engagement). Это не требует запуска атак для принятия A3.

### Открытые вопросы и предложения

Предлагаемый порядок выбора удалённого канала: сначала оценить имеющиеся Run Command и браузерный Bastion Developer для снабжения, запуска подготовленного задания от ограниченного пользователя и сбора результатов. Это не подтверждение пригодности: ограничения egress, объёма передачи и полноты логов должны пройти A3. Если нужен обычный SSH/SCP из локального терминала, определить реальный сетевой путь — приватное подключение либо поддерживаемый Bastion native-client профиль. Приватный IP сам по себе с ноутбука недостижим без такого пути. Новый публичный IP/открытие SSH-порта, VPN или платный upgrade Bastion не включать автоматически. Если имеющийся путь не обеспечивает критерии A3, показать конкретный блокер и стоимость альтернативы.

Испытания оригиналов остаются после приёмки |

Вопросы имеют разные контрольные точки: неизвестная модель не блокирует подготовку AGT budgets, а неподтверждённая граница A3 блокирует его исполнение. Не требовать решения всех поздних вопросов для продолжения документирования.

**Первая проверка A3.2 — доступ самого исполнителя.** Установить, каким способом и из какого приложения пользователь подключался, получить команду/ошибку без ключей и токенов; различить отсутствие сетевого пути, отказ аутентификации и ограничение инструмента агента. Из текущего разрешённого сеанса подтвердить на нужной VM безопасную диагностическую команду (`hostname`/`id`) и полный вывод с кодом завершения; отдельно — перенос и возврат маленького искусственного файла с совпадающими SHA-256. Это критерии будущей проверки, сейчас они не выполнены. Не открывать публичный SSH и не покупать сервис как автоматическое исправление ошибки. Если автоматизированный канал недоступен, сохранить блокер; ручное выполнение пользователем в госте допустимо как отдельный режим, без утверждения об автономной работе агента.

Текущий размер VM — 2 vCPU/4 ГиБ. Он не доказан достаточным для NeMo, Dify или локальной LLM. Перед установкой тяжёлого стека сделать отдельный профиль ресурсов, времени и затрат; размер VM или облачные сервисы не менять молча. Но нехватка ресурсов не отменяет метод из реестра: его статус будет «заблокирован ресурсом» до отдельного решения.

## A4 — последовательность испытаний

Для **каждого** применимого метода выполнить пять проверяемых уровней, где они имеют смысл:

| Уровень | Вопрос | Минимальное доказательство |
|---|---|---|
| E0. Происхождение | Запущены именно неизменённые исходники? | ZIP/файл/commit-статус, SHA-256 в госте, версии зависимостей |
| E1. Штатный тест | Проходит ли тест автора в указанной среде? | Команда, stdout/stderr, exit code; не заменять тест своим |
| E2. Решение | Что выдаёт политика на разрешённом, запрещённом, пограничном и ошибочном входе? | Наши внешние входы и ожидаемый/фактический verdict |
| E3. Реальный эффект | Произошло ли действие после allow и не произошло ли после deny/escalate? | Наблюдаемый тестовый файл, процесс или локальный сервис; лог до/после. Если оригинал даёт только verdict, честный статус «enforcement не проверен» |
| E4. Устойчивость границы | Что при отсутствии настройки, сбое детектора, альтернативном пути вызова, отмене или повторе? | Негативные сценарии, где применимы, с фактическим эффектом и остаточным риском |

Опыты идут короткими лабораторными, по одному методу или одной связанной границе. Минимум: цель; неизменённый источник; искусственные данные; подготовка/откат; команды с местом исполнения; ожидаемое и фактическое; лог и хеши; интерпретация; ограничения. После каждого опыта остановить VM, проверить состояние/затраты и обновить реестр.

Для E3/E4 отделять **защиту стенда** от **испытуемого механизма**. Например, allow-запрос к локальному тестовому приёмнику должен работать, а deny-запрос — блокироваться исследуемой политикой при тех же внешних условиях. Если оба отказали из-за NSG, отсутствующей зависимости или недоступного сервиса, это не успех политики. Исследуемому процессу по умолчанию не давать sudo, Docker socket или полномочия менять защитную конфигурацию; нужда метода в таких правах фиксируется отдельным профилем и проверкой границы.

Порядок не равен приоритету важности:

1. **A4.1 — AGT budgets без LLM.** Оригинальные тесты, входы ниже/на пороге и ошибочные случаи; затем отдельно маршрут от verdict к тестовому инструменту. Нулевые counters штатного Guardian не использовать как демонстрацию лимита.
2. **A4.2 — остальные детерминированные L3.** Allow/block инструментов (DSH, Goose, Hermes), approval/HITL (AGT, DSH, OpenAI Agents, Pydantic AI, Microsoft Agent Framework), лимиты (AGT, Pydantic AI, Dify), sandbox (DSH, OpenAI Agents, Hermes; Dify — с учётом внешнего runtime), egress (AGT, Hermes, Dify), отмена/остановка (DSH, LangGraph, Pydantic AI), аудит/конфигурация. Каждый различный исходный механизм получает собственную строку и результат; общность идеи не заменяет его тест.
3. **A4.2 — L1 и границы данных.** Input rails/moderation NeMo и Dify, недоверенные результаты функций Microsoft Agent Framework, approval сигнала Goose/Hermes; положительные и отрицательные примеры, ошибки детектора, путь до модели и/или инструмента. Не переименовывать NeMo output `injection_detection` в входную prompt-injection защиту. Spotlighting/datamarking/encoding/sandwiching без найденного оригинала остаются пробелами, а не «прошедшими» опытами.
4. **A4.3 — модельный опыт в Azure.** Только после детерминированных маршрутов: отдельно согласовать локальную модель/детектор, runtime, источник весов, объём, стоимость и профиль VM. Проверять косвенную инъекцию из файла/tool output/памяти на синтетических данных: что предложила модель → решение L1/L3 → фактическое действие. Повторить отрицательные сценарии и описать вариативность результатов. Роли сообщений не доказывают внутреннюю иерархию модели. Fine-tuning и ролевые эмбеддинги не имитировать настройками prompt; отсутствие реализации пометить как открытое требование/задачу другой части проекта.
5. **A4.4 — локальная применимость и граница ядра команды.** Повторить критичные сценарии на согласованном целевом ПК/ОС с тем же комплектом исходников, политик и входов; зафиксировать отличия зависимостей/путей/прав. Команда предоставляет ядро и целевой runtime, наша роль — политики/конфигурации и проверка их границы. До повтора результат помечается «Azure подтверждён, локальное применение не подтверждено». Это контрольная точка требования ЧТЗ, а не поручение сейчас запускать архивный код на ноутбуке или возобновлять VirtualBox.
6. **Закрытие A4.** Для каждого требования L1/L2/L3 и смежной границы A1.4 сделать ссылку на run-id, проваленный опыт или точный блокер. Провал политики — результат испытания, не повод спрятать метод. Сравнить каждый результат с собственным `policy-gateway` только как отдельную адаптацию, не как доказательство upstream. Открытые Q1/Q7 и невыполненную A4.4 сохранить в передаваемом отчёте; полное локальное соответствие при этом не заявлять.

GenAI Red Team Lab и другие атакующие корпуса могут дать безопасные синтетические сценарии; OWASP CheatSheetSeries — критерии/рекомендации. Их нельзя засчитать как работающие политики. Сканеры и внешние runtime учитывать по собственному назначению и зависимостям. Не запускать весь ZIP или неоценённый тестовый стенд лишь ради отметки «архив испытан».

## Протокол, статусы и остановка

Каждый запуск создаёт `logs/runs/<run-id>/` по [плану](План_аудита_оригиналов_на_согласование.md): команды, UTC-время, версии/хеши, отдельные ожидаемые и наблюдаемые значения, stdout/stderr и проверка эффекта. Сырые журналы остаются в госте; в проект переносить только просмотренные обезличенные копии. Оригинал ради логирования не менять.

Статусы независимы: **точная копия / изменён / неизвестно**; **не запускался / тест прошёл / тест провалился / блокер**; **только verdict / реальный эффект проверен / интеграция в агент команды не проверена**. Блокер должен содержать воспроизводимую причину, предпринятые безопасные шаги и условие возобновления. «Полностью проверено» относится только к фактически испытанному методу и уровню; весь модуль нельзя принять, пока требуемые границы остаются заблокированными или отсутствуют.

До согласования этой редакции разрешены только чтение, уточнение реестра и проектирование A3. Эта программа сама по себе не запускает VM, не разрешает облачные расходы, установку стеков, испытание политики или отправку в Git.
